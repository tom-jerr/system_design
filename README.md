# Systems in Rust：用 AI Agent 练习系统设计

这个仓库用 Rust 实现 [MIT 6.5840](https://6.5840.github.io/) 的分布式系统实验，以及从经典系统论文中挑选的机制。目标不只是“把功能做出来”，而是通过阅读、建模、实现、故障注入和复盘，训练系统判断力：看清楚保证与假设，找到真正重要的边界情况，用尽量直接的设计解决问题，并能与 AI Agent 一起快速验证想法、定位 bug 和审视设计。

AI Agent 是结对探索和调试的伙伴。设计取舍和最终实现仍要能由维护者解释、验证和负责。项目偏好小而清楚、由不变量支撑的实现；避免没有需求依据的抽象层、框架化设计和堆叠防御式检查。

## 设计与第三方库选择

每个实现先写清楚要解决的问题、目标场景、必须提供的保证和主要约束，再选择合适的成熟第三方库。不同场景可以选不同库；不追求全仓库统一成一个“标准栈”。只有当学习目标要求亲自实现某个核心机制时，才自己实现它；其余通用部件优先复用语义匹配的成熟实现。

Agent 必须遵循 [`docs/DESIGN_RULES.md`](docs/DESIGN_RULES.md) 中的设计规则。规则以 DDIA 对可靠性、可扩展性、可维护性和技术取舍的分析为基础，并结合作者博客中“先理解机制、再比较实现”和用测试具体验证行为的经验，转化成本仓库的工程约定。规则也明确区分了来源中的经验与本项目据此作出的推论。

## 当前进度

当前仓库包含一个单机多进程 MapReduce 实现：

- `shard_kv/mapreduce/`：使用 Tokio 和 Unix domain sockets 实现 Coordinator/Worker、Map/Reduce 执行、attempt fencing、租约、心跳、Map 输出 manifest 和故障恢复。
- `shard_kv/mapreduce/docs/MAPREDUCE_FAILURE_DESIGN.md`：协议、状态机、租约边界、失败处理与恢复设计。
- `shard_kv/mapreduce/tests/`：与顺序参考实现对比的正确性测试和 worker 崩溃恢复场景。

这是一个学习用的单机原型：Coordinator 状态保存在内存中，Worker 通过本机 UDS 通信，输入文件对进程可见。它还不是可多机部署或 Coordinator 重启后可恢复的集群。目录名中的 `shard_kv` 也不代表当前已有 ShardKV 实现。

## 学习路线

以 6.5840 的实验主题建立分布式系统基础，再用经典论文补足真实系统中的设计背景。每个主题都遵循同一个闭环：先写清楚接口和保证，再构造最小实现，用可重复的测试或故障场景验证，最后记录设计为何成立以及它的边界。

建议逐步覆盖：

1. MapReduce：任务调度、数据流、重试、幂等与失败恢复。当前实现和设计说明见 [`shard_kv/mapreduce/`](shard_kv/mapreduce/README.md)。
2. Raft：选举、日志复制、安全性、持久化与 snapshot。
3. Key/Value 服务：线性一致性、重复请求处理、客户端重试与状态机应用。
4. ShardKV：分片配置、迁移、配置变更期间的并发与故障。
5. 结合论文扩展：围绕具体实现问题选择论文，复现关键机制或设计实验，不以“论文清单”代替可验证的工程结果。

这些是路线图，不是当前完成状态。每新增一个实验或论文实现，应在对应目录记录其范围、运行方式、核心不变量、已知限制和验证证据。

## 与 AI Agent 协作

每次任务尽量从一个可回答的系统问题开始，例如：“Coordinator 在 worker 超时后重派任务时，旧 worker 的迟到提交能否覆盖新结果？”让 Agent 先定位相关状态和代码，明确假设、正确性约束与最小验证方式，再提出小范围修改。

协作时重点检查：

- **不变量与边界**：状态何时改变？谁有权改变？超时边界、重复/乱序消息、崩溃时刻和重启语义是什么？
- **证据与验证**：论文和实验要求是什么？哪条测试或故障注入能区分正确与错误？测试结果能证明什么、不能证明什么？
- **设计成本**：每个抽象、状态字段、锁、重试或错误分支解决哪个已知问题？有没有更小的方案？
- **共同调试**：从复现步骤、日志和状态迁移出发；先缩小故障范围，再修复根因，避免用更多分支掩盖不清楚的状态模型。
- **审查 Agent 输出**：核对实际 diff、并发语义、资源生命周期和错误路径；Agent 的解释不是正确性证据。

## 开始使用

MapReduce crate 位于子目录中：

```sh
cd shard_kv/mapreduce
cargo build --bins
```

更多运行示例、应用列表、环境变量及测试说明见 [`shard_kv/mapreduce/README.md`](shard_kv/mapreduce/README.md)。

## 设计记录

重要设计应靠近对应实验记录：问题与约束、依赖的论文机制、关键不变量、状态转换、失败场景、验证结果和未覆盖边界。涉及第三方库时，说明目标场景、选型依据、库提供的保证及其限制。记录结论时区分论文明确给出的保证、实现自行选择的策略，以及尚未验证的假设。
