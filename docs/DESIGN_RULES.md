# 系统设计与第三方库选型规则

这份规则把 DDIA 对数据系统的分析方法转成仓库工作约定。DDIA 强调从具体应用需求出发，比较不同技术的内部机制、保证和取舍，而不是脱离场景给出单一技术答案；书中的可靠性、可扩展性和可维护性也是本仓库讨论设计的共同坐标。[DDIA 原书介绍](https://martin.kleppmann.com/2017/03/27/designing-data-intensive-applications.html)；[作者谈技术比较与理解内部机制](https://martin.kleppmann.com/2014/09/15/writing-a-book.html)。

下面关于如何挑选 Rust crate、何时自己实现的条目，是本仓库根据这些经验制定的工程规则，并非声称它们是 DDIA 的逐字结论。

## 从 DDIA 解读中提炼的系统设计准则

这些准则综合了 DDIA 第一版第 1、3–9 章的主题、作者公开文章，以及独立读书笔记。独立笔记用于帮助发现实践问题，不视为规格或权威来源；遇到保证、算法语义和库行为时，回到原书、论文、官方文档、源码或实验。

### 1. 把意图写成可检查的需求

区分功能需求和质量属性。把“快、可靠、可扩展”改写成负载参数、目标指标和故障条件：哪些操作、数据量/增长方式、请求分布、吞吐、p95/p99 延迟、可接受的数据丢失/不可用窗口，以及哪些故障必须承受。观察偏斜和热点，不用平均值代替真实分布。没有需求证据时，不先引入分片、复制、缓存或异步处理。

### 2. 先比较机制，再选择具体技术

从能力和语义出发比较方案：例如 B-Tree 与 LSM 的读写/空间取舍，单领导者与多领导者复制把冲突放在哪里，批处理与流处理如何处理有界/无界数据。技术产品是这些机制的具体实现，名称、热度或 API 熟悉度不能代替语义比较。作者介绍 DDIA 的结构时明确采用“先讲解决问题的概念和取舍，再展示哪些软件采用该机制”的方式。[作者：Drawing a map of distributed data systems](https://martin.kleppmann.com/2017/03/15/map-distributed-data-systems.html)

### 3. 组合组件时，端到端系统责任仍在应用

数据库、缓存、索引、队列和批/流处理器各自提供局部能力；把它们连接起来的应用代码也构成数据系统。明确每份数据的权威来源、派生副本如何更新/重建、更新部分失败后如何恢复，以及调用者能观察到什么。组件各自正确，不自动推出组合后的一致性或原子性。[DDIA 第 1 章目录与内容](https://www.oreilly.com/library/view/designing-data-intensive-applications/9781491903063/ch01.html)；[章节解读：多个工具组合后的责任](https://paramcodes.github.io/ddia/chapters/ddia-chapter-1.html)

### 4. 明确保证，再选择最小充分语义

把一致性、持久性、排序、事务隔离、交付/去重和可用性写成调用者可观察的承诺。描述违反承诺时会出现的具体异常，例如读己之写丢失、读结果倒退、因果顺序颠倒、丢失更新或写偏斜。然后只选择满足需求的最小机制，并为它付出的延迟、吞吐、可用性和运维复杂度负责。不要把“强一致最好”或“最终一致更快”当作脱离产品语义的通用答案。

### 5. 把超时看作不确定性，设计安全重试

超时只能说明在期限内没有收到响应，不能证明远端没有执行。重试可能重复副作用，也可能把额外负载推给已经拥塞的系统。对重试定义可重放性、幂等键或去重边界、最大次数/退避与错误分类；对租约/锁保护的资源用递增 fencing token 拒绝迟到的旧持有者。测量目标环境的延迟分布来调超时；用单调时钟计算本地时长，不跨机器比较本地单调时间。作者关于分布式锁的文章解释了暂停进程和过期租约的风险；DDIA 第 8 章解读也强调超时无法区分请求丢失、延迟和回复丢失。[作者：How to do distributed locking](https://martin.kleppmann.com/2016/02/08/how-to-do-distributed-locking.html)；[DDIA 第 8 章解读](https://paramcodes.github.io/ddia/chapters/ddia-chapter-8.html)

### 6. 让关键保证可被反例测试

把口头保证改写成能失败的场景：并发操作产生哪种异常、一个节点暂停或断连会怎样、重复提交是否改变结果、崩溃发生在写入/确认之间会留下什么状态。针对每个关键不变量构造最小反例测试或故障注入，并说明测试的模型和盲区。DDIA 作者创建 Hermitage 的动机正是把数据库隔离级别转换为具体竞争场景，指出同名隔离级别在不同数据库上可能提供不同保证。[Hermitage：Testing the “I” in ACID](https://martin.kleppmann.com/2014/11/25/hermitage-testing-the-i-in-acid.html)

### 7. 为增长设计选项，不凭空承诺“可扩展”

说明负载如何增长，以及当前瓶颈和下一种可行扩展是什么。识别扇出、尾延迟、排队、热点 key 和跨分区操作成本；评估分区键对读写路径、重平衡和热点的影响。规模化策略需由测量或明确目标支撑；如果当前单机足够，记录它的限制和何时需要演进即可。

### 8. 把简单性、可运维性和可演进性作为设计结果

关注偶然复杂度：重复状态、紧耦合、特殊情况、难以观测的后台流程，以及必须靠人工猜测才能恢复的故障。选择让状态和失败可见、可以重放/重建、能分步迁移的方案。简单不是少写功能，而是让实现复杂度主要对应真实问题。DDIA 第 1 章将可靠性、可扩展性与可维护性并列，并把可操作、简单和易演进作为维护系统的核心维度。[O’Reilly：DDIA 第 1 章](https://www.oreilly.com/library/view/designing-data-intensive-applications/9781491903063/ch01.html)

### 9. 说明规则的证据来源和适用边界

每条设计结论都要能回答：它来自课程规格、论文/原书、库文档、源码、测试还是当前假设？哪些前提改变会让结论失效？DDIA 相关读书会实践也强调将概念联系到团队真实系统和设计取舍，而不是背诵术语。[Medium 的 DDIA 读书会方法](https://jacob.blog/notes/book-club/)

### 参考资料分层

- **原书与作者材料**：优先依据 [DDIA 原书页面](https://www.oreilly.com/library/view/designing-data-intensive-applications/9781491903063/ch01.html) 和 [作者文章索引/书籍说明](https://martin.kleppmann.com/2017/03/27/designing-data-intensive-applications.html)。涉及具体机制时继续追到书中引用的论文、系统文档或源码。
- **作者的研究实践**：[Hermitage](https://martin.kleppmann.com/2014/11/25/hermitage-testing-the-i-in-acid.html) 展示如何将抽象保证转为可复现测试；[分布式锁文章](https://martin.kleppmann.com/2016/02/08/how-to-do-distributed-locking.html) 展示租约、暂停和 fencing 的交互。
- **独立章节解读**：[DDIA Chapter 1 Study Guide](https://paramcodes.github.io/ddia/chapters/ddia-chapter-1.html)、[Chapter 8 Study Guide](https://paramcodes.github.io/ddia/chapters/ddia-chapter-8.html)、[Replication 读书笔记](https://blog.aidan.tw/en/blog/ddia-replication/)帮助快速定位问题与反例。它们是个人解读，其中的建议需要结合原书、实现语义和本项目场景重新判断。
- **实践讨论方法**：[Medium 的 DDIA 读书会记录](https://jacob.blog/notes/book-club/)强调把概念联系到实际系统、调试经验和代价讨论，适合作为本仓库学习复盘的参考。

## Agent 必须遵循的规则

### 1. 先定义意图与场景，再设计和选库

开始实现前，先用简短文字说明：

- 要解决什么问题，谁会使用这段实现？
- 运行在什么场景：单机还是多机、学习原型还是生产负载、数据规模和故障模型是什么？
- 必须保持哪些正确性保证，例如持久性、一致性、顺序、去重、恢复语义？
- 主要约束是什么：延迟、吞吐、资源、可移植性、依赖复杂度、可观察性或学习目标？
- 用什么最小实验或测试判断方案有效？

不要从“我知道某个库”或“项目其他地方用了某个库”倒推需求。没有明确负载时，不虚构容量目标；没有必要时，单机与简单方案是有效基线。

### 2. 每个问题按场景选合适的成熟库

把需求拆成需要的能力，再比较候选库实际提供的语义。不同实验和运行场景可以使用不同库；不要为了表面一致强行统一依赖。

选型至少核对：

- **语义是否匹配**：数据模型、持久性/一致性、消息交付语义、排序、事务边界、取消行为和错误语义是否满足需求？
- **失败如何表现**：超时、断连、磁盘错误、重试、部分成功和恢复由谁处理？库的 API 是否让这些情况可见？
- **适用范围**：单机/多机、同步/异步、数据量和访问模式是否与目标场景相符？
- **工程成熟度**：文档、维护状态、兼容性、平台支持、依赖树和安全更新路径是否可接受？如果这些信息可能变化，选型时查当前的一手资料，不凭记忆断言。
- **复杂度成本**：引入它带来哪些概念、配置、运行依赖和调试成本？现有标准库或更简单的库是否已经足够？

比较应围绕关键差异展开，不必为每项任务制作冗长的库评估表。只有候选方案的差别会改变系统保证或显著改变成本时，才详细记录比较。

### 3. 明确哪些机制要自己实现

本仓库的学习目标可能就是理解某个机制，例如 Raft 的选举与日志复制、MapReduce 的任务重试，或存储引擎的写入路径。此时可以亲自实现目标机制，但不要顺手重造与学习目标无关的通用设施。

如果第三方库会遮蔽本次要学习的机制，可以把它限制在边界之外，或暂时不采用；在设计记录里写明这是教学/实验选择，以及生产系统通常会复用哪类成熟组件。反过来，如果任务只需要网络传输、序列化、临时目录等常规能力，优先评估成熟库，避免无意中把它们变成新的研究项目。

### 4. 依赖库不等于转移正确性责任

把库的文档保证、当前配置、调用方式和本项目自己的保证分开说明。检查库的关键行为是否依赖隐含前提，例如调用顺序、持久化配置、幂等键、事务隔离级别、连接池生命周期或重试策略。

在系统边界测试真实语义：故障注入、重复请求、断连、进程重启、并发冲突或数据恢复。单测覆盖了包装代码，不等于证明底层库或组合系统满足端到端保证。对不可观测的行为不要作强保证承诺。

### 5. 用具体证据比较机制，而不是只比 API 或名气

DDIA 作者在介绍写作方法时强调，技术比较不能只停留在 API、性能数字或许可等表面属性，还要理解系统如何工作；其对数据库隔离级别的研究也用具体 anomaly 测试描述系统实际行为。[作者博客：写作 DDIA 的动机](https://martin.kleppmann.com/2014/09/15/writing-a-book.html)；[Hermitage：用测试检查 ACID 隔离性](https://martin.kleppmann.com/2014/11/25/hermitage-testing-the-i-in-acid.html)。

因此，Agent 应优先找官方文档、论文、源码和能复现的实验来回答“它到底保证什么”。性能基准必须贴合目标工作负载；通用排行榜和单一 benchmark 不能替代场景分析。

### 6. 控制抽象和防御逻辑

每个依赖、包装层、状态字段、重试、超时、检查和错误分支都要对应一个当前需求或已识别失败模式。若解释不出它保护的保证，先不要添加。使用库不能成为再包一层通用框架的理由；封装应隐藏本项目不想重复处理的细节，同时保留重要错误和语义。

### 7. 记录选型决策和剩余边界

当选型会影响系统保证、替换成本或运行方式时，在对应模块的设计文档记录：

1. 意图、场景和约束；
2. 必须提供的语义与失败模型；
3. 选择的库/机制及理由；
4. 一个关键替代方案及为何不选（若确有实质差异）；
5. 验证证据、已知限制和未覆盖情形。

小型无争议依赖不要求单独写 ADR；在局部 README 或代码注释中交代即可。文档要帮助未来维护者重新评估，而不是为选型辩护。

## 可复用的决策顺序

```text
问题与场景
    ↓
正确性保证与故障模型
    ↓
负载和工程约束
    ↓
目标机制是否属于本次学习内容？ ── 是 → 自己实现该机制，复用周边设施
    │
    否
    ↓
比较成熟库的语义、失败行为与维护成本
    ↓
做最小原型/针对性验证
    ↓
记录选择、证据与边界
```
