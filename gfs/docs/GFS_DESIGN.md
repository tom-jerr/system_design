# GFS 详细设计：租约、复制、负载均衡、快照、COW 与 GC

状态：**设计基线，尚未实现或验证**。记录日期：2026-10-30。模块现状和分阶段退出条件见[模块 README](../README.md)。本文的工程协议、阈值和恢复策略是本项目的选择，不声称它们由论文完整给出。

## 1. 意图、依据与故障模型

### 1.1 要解决的问题

以 Rust 复现 GFS 对大文件、顺序数据访问、普通覆盖写和并发 record append 的机制。学习重点是状态权威来源、复制顺序、租约失效与在途操作、失败写入、COW 发布及延迟回收，而非自行实现 RPC 框架、共识算法或事务存储引擎。

先在 Linux 单机多进程运行，再用相同 TCP 协议部署到多机。数据目录各自独立，不依赖共享文件系统。性能目标先通过实验定义，不预先承诺吞吐、延迟或集群容量。

### 1.3 假设与范围

- 进程可能崩溃、暂停、重启，网络可能丢请求／回复、延迟、重排和分区；超时是失败怀疑，不是失败证明。
- 磁盘可能返回错误、部分写入或出现校验不匹配。持久化保证依赖文件系统、块设备和硬件正确履行同步调用；不将进程 kill 测试当作断电测试。
- 节点遵循协议，不处理拜占庭节点或恶意伪造控制请求；首版在可信实验网络运行。NodeId 和数据目录不克隆给另一个活动实例。
- 使用持续推进的 `CLOCK_BOOTTIME`，时钟速率误差有界；任意冻结的虚拟机时钟不在模型内。该速率界须是部署假设，单调时钟 API 自身不证明该界。
- 活性依赖网络与调度最终恢复、时钟推进、足够健康副本和足够磁盘空间。Master 丢失多数派时不能提交新元数据决策。
- 三副本不能容忍所有副本同时损坏；全部来源为 dirty 或失去时允许返回不可用并保留现场。

## 2. 组件、所有权和持久状态

### 2.1 成熟组件的边界

| --- | --- | --- |
| 异步调度、网络、阻塞工作池 | Tokio | 独立 chunk 并行，阻塞磁盘工作受限；不在 runtime 工作线程直接阻塞数据库事务 |

### 2.2 Master 与 chunkserver

三个 Master 组成一个 Raft 组。只有当前领导者驱动授租、复制、快照和 GC；followers 不自行发出后台变更。客户端查询经 OpenRaft 的线性一致读屏障并等待状态应用后读取元数据；文件内容仍不因此获得线性一致性。[OpenRaft ensure_linearizable](https://docs.rs/openraft/0.9.25/openraft/raft/struct.Raft.html#method.ensure_linearizable)

文件内容从客户端直接流向 chunkserver，修复在 chunkserver 之间传输。Master 不转发内容，也不在 Raft 日志中记录 chunk payload。

每个本地 chunk 有独立的串行执行边界，覆盖 mutation、权限切换、副本发布和退休。磁盘操作进入受限工作池，读／复制持有本地引用，删除须等待它们释放。不同 chunk 可以并行，不能把网络调用和磁盘等待放进一个全局状态锁。

### 2.3 状态权威来源

| 对象 | 持久字段或记录 | 运行时补充 |
| --- | --- | --- |
| 文件 | FileId、路径、映射版本、chunk 列表、正常／隐藏删除状态、复制目标 | 路径范围冲突索引 |
| chunk | ChunkId、内容版本、映射引用数、租约决策、维护意图与操作 pin | 当前验证过的实际副本位置 |
| 长操作 | OperationId、类型、阶段、源版本、目标身份、已分配资源、路径／chunk 占用 | RPC 任务和本地重试时间 |
| 本地副本 | ReplicaId、ChunkId、版本、长度、块校验和、dirty、租约授权／撤销、删除意图 | 打开文件、本地读引用、工作队列 |
| 节点 | 稳定 NodeId；数据目录独占 | BootId、报告序号、接收时间、容量／队列／流量 |

FileId、ChunkId 使用 Raft 状态机中的持久单调分配器；状态转换内分配，不在 apply 中生成随机身份。ReplicaId 和 OperationId 同样必须唯一且不复用。BootId 标识一次进程启动，所有授租回复和在途操作校验相应身份。

Raft 持久化负责投票、日志、已应用位置、成员信息、应用状态和完整 snapshot。redb 写入使用立即持久化；只有达到相应存储契约的持久化点才能完成回调。snapshot 应用状态、已应用日志位置和成员信息必须来自同一个一致视图，安装成功前不能清除恢复所需日志。

实际位置、心跳和负载由 inventory 重建；持久化计划和旧 RPC 回执不是节点当前存活的证明。Master 恢复完成前不能根据暂时为空的内存索引删除副本。

### 2.4 共同不变量与长操作

1. 一个 chunk 的一个租约代次只有一个 primary，参与副本集合固定。
2. 映射引用数大于一的 chunk 不接受修改，首次修改必须 COW。
3. 本地执行前校验版本、holder、BootId、lease ID、序号、期限与撤销状态。
4. 新副本先验证并持久化，随后才能发布；文件映射与引用数在同一事务内切换。
5. GC 不删除映射或进行中操作仍依赖的 chunk，退休身份不能重新成为活动身份。
6. 版本与身份不回退、不复用；所有递增检查溢出，失败时状态不变。
7. Raft apply 确定性执行，不等待网络、读本地时钟或依赖本节点实时负载作决定。

长操作以 `Preparing / Committed / Aborted` 等明确阶段保存；完成和终止均需提交，重放按 OperationId 与预期阶段幂等。恢复后重新检查本地持久状态，不能仅相信旧进程的内存确认。

命名空间逻辑上使用完整路径到文件元数据的映射，不支持硬链接或符号链接。路径规范化在 RPC 边界完成。申请操作时原子检查并登记所需路径范围与 chunk 集合；冲突返回 Busy，不先占有一半再等待另一半。处理顺序为路径层级与字典序，再按 ChunkId。该机制防止 create、rename、delete、snapshot 和 COW 绕过彼此的范围保护。

维护操作不会全局阻塞无关文件；冲突操作不承诺无界竞争下的公平性。RPC 超时或取消不自动释放已提交的占用，新领导从意图恢复它们。

## 3. 租约与权限恢复

### 3.1 身份、阶段和时间

租约记录包含 `chunk_id`、`chunk_version`、`lease_id`、primary 的 NodeId/BootId、固定参与 ReplicaId 集合、请求 nonce、最长时长和阶段。lease ID 使用已提交 PrepareLease 的日志身份。

chunk version 标识内容代次，lease ID 标识具体授租。撤销 lease ID 不必增加内容版本。每个副本持久保存已授权／撤销的租约状态，同一个 lease ID 的撤销是终态，迟到 Activate 不能将其恢复。

| 阶段 | 可观察行为 |
| --- | --- |
| NoLease | 可以读，没有修改权限 |
| Preparing | 决策已提交，正在安装新版本与权限；不向客户端发布 |
| Active | 可返回 primary；其本地有效期限内可接受修改 |
| Draining | 禁止新授权和续租，停止接受旧权限下的新操作并排空已有操作 |
| Frozen | 本次维护选择的可信来源已经冻结，可复制、共享或调整布局 |

阶段是逻辑授权状态，不替代期限检查。Master 不能把本地 Instant 写入状态机给其他机器比较；chunkserver 重启后不从旧持久记录恢复可用的本地租约期限。

### 3.2 授租

1. Master 检查 chunk 不受冲突操作占用；共享 chunk 先走 COW。默认需要三个验证过的健康副本。
2. 从副本中选择 primary。primary 发送带 nonce 的授租请求，在发送前记录本地起始时刻。
3. Master 提交 PrepareLease：增加内容版本，保存 lease ID、holder、固定参与者和最长时长。
4. 副本在本地串行队列中安装新版本与指定权限，持久化后确认。旧版本、旧启动身份和已撤销的相同 lease ID 不能激活。
5. primary 只接收与当前请求、nonce 和 BootId 匹配且剩余时间为正的授权；期限从请求发送前计算。
6. 所有参与者确认后，Master 提交完成状态，向客户端发布布局和 primary。

Preparing 期间的授权来自已提交的准备意图，但客户端尚不能取得它。准备操作与维护操作冲突；快照不能插入准备中途并遗漏随后到达的授权。

中断后可恢复相同准备意图或提交终止；已分配版本不能回退。恢复须区分“部分节点安装了新版本但尚未发布”的准备记录和已发布的写租约，不能将低版本副本随意提升为数据来源。对于后者，错过 mutation 的旧版本副本不能因状态干净就算健康。

节点报告高于 Master 记录的未知版本时隔离调查。本项目先提交版本决策再执行节点动作，故不能采用原论文在另一日志故障模型下直接采纳更高版本的策略。

### 3.3 续租和期限边界

默认最长租约 T 为 60 秒，心跳 1 秒；有写入活动或待执行 mutation 的 primary 每 20 秒尝试续租，空闲时自然过期。续租请求可合并在心跳中，但 grant 必须在 Raft 提交后回复。

续租匹配当前 chunk version、lease ID、holder、BootId 和未进入 Draining 的阶段。primary 对每次请求保留发送前起始时刻；网络重试复用该请求 nonce 和起点。回复不匹配、已过期或已撤销时不延长期限。

- `now < deadline` 才能接受新修改；等于期限即失效。
- 续租超时仅意味着结果不确定，最多使用最后确认的本地期限。
- 回复迟到不能从接收时重新起算 60 秒。
- 取消续租任务不是安全边界，最终由资源端校验并拒绝操作。

时钟使用 Linux CLOCK_BOOTTIME。若 primary 和接管 Master 的时钟速率误差都至多为 ρ，Master 等待的本地时长保守取 `ceil(T × (1 + ρ) / (1 - ρ))`。推导为 primary 的 T 最长可持续实际时间 `T/(1-ρ)`，而等待者的时钟最快按 `1+ρ` 推进。部署必须给出并验证可接受的 ρ，不能拿未经确认的常数作为安全证据。

CLOCK_BOOTTIME 包含暂停／休眠期间的时间推进，但不证明虚拟化环境不会冻结该时钟。OpenRaft 的 leader lease 只解决其共识协议问题，不等于 chunk 租约。[OpenRaft leader lease](https://docs.rs/openraft/0.9.25/openraft/docs/data/leader_lease/index.html)

### 3.4 撤销与排空

1. 提交维护意图，将 chunk 转入 Draining，拒绝新授租／续租。
2. 发送 RevokeLease，绑定 lease ID、版本与副本身份。
3. 副本停止接受该权限的新操作；之前已接受的操作完成或以明确错误结束。
4. 在与 mutation 相同的串行边界持久化撤销，再回复冻结确认；成功确认后同一 lease ID 不能重新激活。
5. 维护只使用已冻结、校验通过的来源，保留必要操作 pin。

租约过期只限制新的操作准入，不撤销此前排队、进行中的磁盘 I/O 或发往 secondary 的 RPC。版本安装也必须与这些操作串行，避免先安装新代次再被旧写覆盖。

副本不可达时，等待旧 primary 权限的保守上界，将未确认冻结的副本排除；不能拿它作为快照或复制来源。重新加入时校验其撤销与维护状态，必要时从可信来源重建；即使内容 version 相同也不能直接宣布健康。

### 3.5 Master 切换与重启

新领导提交领导代次屏障、恢复状态机和操作意图、重建 inventory，从屏障起等待旧授权最长可能存活时间。旧领导不能用只存在于内存的心跳决定授权；旧的迟到回复受 primary 请求起点约束。

恢复授租前，对实际使用的副本执行撤销／排空，再安装新版本与权限。已经缓存布局的读取可继续；新的元数据读取需屏障和就绪的位置索引。GC 也必须等待元数据完整恢复。

未完成 snapshot、COW、复制和 GC 不能因进程切换而丢弃占用；根据持久阶段继续或提交终止。切换期间可延后写入恢复约一个租约周期，不承诺瞬时接管。

## 4. 数据路径、一致性和本地恢复

### 4.1 数据推送与控制分离

客户端先解析 FileId、映射版本和 chunk 布局，之后直接访问 chunkserver。读、mutation、复制带预期内容版本和相应实例身份；遇到陈旧布局、错误或提前 EOF 时刷新，重新打开文件时清除旧布局缓存。

数据按 256 KiB 帧沿副本链即时转发，不等整个 payload 收完才转下一站。链顺序依据显式主机／机架标签和可测网络距离选择，不要求 primary 在第一站。控制流仍是客户端到 primary，再到 secondaries。

连接复用，但数据、控制与 Raft 流量使用独立连接。数据暂存按字节计费并有上限，执行中的 payload 持有引用；未进入执行且被淘汰的 payload 返回缺失，由客户端重推。队列和磁盘工作也需有界，不能借大 RPC 消息上限规避内存约束。

### 4.2 普通 mutation

大写按 chunk 边界与有限的操作大小拆分。primary 为 chunk 分配单调序号，先本地持久执行，再转发到固定 secondaries；它们按同一序号执行。所有参与者持久完成后才返回成功。

首版每个 chunk 只执行一个 mutation，不同 chunk 并行。对重复控制请求只在有匹配身份与已知结果时复用结果；不能仅因序号较小就把未知请求报告成功。检测序号缺口、版本错误或任意执行结果不确定时，停止本代次后续修改并恢复，不静默跳过或扩大重试。

部分成功可能留下不一致区间；不能把 secondary RPC 超时当作该节点未写入。primary 在错误后冻结后续 stream，重新恢复并授租；同一代次不静默缩小参与者集合。

### 4.3 本地写入和校验

本地副本修改固定顺序：

```text
在串行边界检查版本、权限、序号与保留字节的校验
→ redb Immediate 提交 dirty
→ 修改普通数据文件并完成同步
→ redb Immediate 原子保存长度、校验和、序号并清除 dirty
→ 返回完成
```

部分覆盖前读取并验证保留字节所在的边界块，避免以新校验和掩盖既有损坏。首版校验每个受影响块，校验通过前不把对应数据块发给客户端或复制目标。流式读取中后续块失败可能发生在前面块已经发送之后，客户端必须保留部分完成状态，不能将整个读宣称为原子成功。

创建、替换和删除数据文件还需同步父目录。数据文件位置只由本地受控身份生成，不把客户端路径拼成节点文件路径。

磁盘写入或同步错误使副本退出健康集合；不依赖后一次同步成功清除先前失败的不确定性。Linux 的 writeback 错误报告不等同每次调用独立成功证明。[Linux VFS 错误处理说明](https://www.kernel.org/doc/html/latest/filesystems/vfs.html)

重启遇到 dirty、校验不匹配或不符合已提交版本的状态时隔离，不能读取现有字节后重新生成校验和宣布恢复。由健康来源重建；全部来源不可用时返回错误、保留现场。

该协议复用 redb 而不自写完整 WAL，但一次小写可能需要多个同步屏障，且在后续失败写期间所有副本同时崩溃时可能全部被隔离。它不是事务文件存储；后续批量持久化必须继续满足以上顺序。

### 4.4 record append 与可观察语义

record append 最大为 chunk 的四分之一，即 16 MiB。primary 选择偏移；空间不足时将 chunk padding 到 64 MiB，通知参与者执行后让客户端转到下一 chunk。

成功要求记录在所有参与者的同一偏移完整写入。重新授租后，以参与副本已验证长度的最大值选择追加起点，保留可能的失败尾部，不截断到最短副本并声称保留原始 GFS 语义。

回复丢失后重试可产生重复，失败区间可能有残片或副本间差异。示例记录工具包含记录 ID、长度和校验，帮助应用识别有效记录与去重；文件系统不提供恰好一次。

命名空间修改有原子提交顺序；跨 chunk 写不构成事务，并发覆盖写可能交错。stat 的并发长度只是观测，不构成原子内容视图。失败写和读缓存允许的陈旧窗口遵循论文的宽松模型，元数据读屏障不会改变这些性质。

客户端区分确定拒绝、刷新布局重试与结果不确定；执行重试受调用截止时间限制。取消通知不撤回已提交的元数据或磁盘操作，不吞掉数据损坏、磁盘错误、编解码等确定性错误。

## 5. 放置、修复与负载均衡

### 5.1 观测与副本放置

节点报告容量、可用空间、创建／复制占用、读写队列、吞吐和 primary 数。Master 按当前 BootId 和报告序号接收，记录本地接收时间；负载样本不逐条写入 Raft。新领导未收集报告前不把历史位置当作就绪状态。

创建候选按以下顺序筛选和比较：

1. 排除未注册、疑似失联、磁盘错误、已持有同 chunk 副本的节点。
2. 优先跨物理主机和机架；拓扑不足时明确记录实际分布，不能声称具备机架故障容忍。
3. 可用空间减去正在创建／复制的预留，并保留总容量的 5% 运维空间；拒绝明显放不下的目标。
4. 在满足故障域约束的候选中，依次比较容量使用率、近期创建／复制负载、队列，最后用 NodeId 稳定打破平局。
5. 选择结果作为意图提交，节点创建并验证后再发布实际位置。

按需分配文件和 reflink 的未来写入仍可能 ENOSPC，预留不承诺整个租约生命周期无空间错误。primary 在副本集合内按 mutation 队列、primary 数、NodeId 选择，与推送链首站分开。

### 5.2 修复和迁移

修复优先级：只剩一个健康副本；阻塞前台；其他正常文件欠复制；隐藏删除文件欠复制。同级按等待时间和 ChunkId 排序。

复制流程：

```text
提交操作意图，pin 来源和创建中的目标
→ 冻结、排空并验证来源
→ 目标按独立 ReplicaId 创建临时文件
→ 流式复制，用来源已有校验和验证
→ 数据及目录项持久化，本地标记 Ready
→ 提交新副本进入布局
→ 释放 pin 与冻结
```

首版暂停该 chunk 的修改完成复制，读取继续，暂不实现在线增量追赶。发布检查 OperationId、预期版本、源身份和操作仍未终止；终止后的迟到 Ready 不能发布。

校验分别验证副本本身，不把多数副本摘要相同当作正确性依据。GFS 失败区间可能合法不同；修复可从健康来源取完整副本，但不能恢复失败写的唯一最终结果。没有来源时保留坏副本并返回不可用。

迁移先复制增加新副本，再提交旧实例退休。退休前重新检查当前仍有复制目标数量的健康副本、故障域满足策略且没有相关 pin。目标在这期间失效则停止退休，不能凭更早的 Ready 回执删除来源。客户端访问旧位置失败时刷新；已打开的本地读引用由删除队列排空。

### 5.3 容量与 primary 均衡

下列是实验初值，属于工程假设：

- 每 60 秒评估；节点使用率超过集群容量加权平均值 10 个百分点时启动容量迁移，目标节点低于均值。
- 来源回到均值以上 3 个百分点内停止，形成滞回。
- 优先选无活动写租约、近期写流量低的 chunk；容量和活跃写无法同时改善时暂缓低优先级迁移并报告阻塞原因。
- 每节点最多一个复制输入和一个复制输出，全局最多四个。来源和目标额度同时满足后才执行，不能占住一侧无限等待另一侧。

自然授租先平衡 primary。持续租约在维护轮次中比较：两个节点 primary 数相差至少两个，且低负载节点持有目标副本时，每轮最多转移一个租约；同一 chunk 冷却两个租约周期。转移执行完整撤销、排空和新授租，不能改写一个 holder 字段。

这些指标不自动等价于异构节点的利用率，也不承诺消除单个写热点；需记录实际队列和负载来评估是否调整策略。

### 5.4 读取分散与后台流量

客户端优先选择网络位置相近的副本，再根据本地延迟与在途请求分散读取。错误或提前 EOF 时刷新位置。显式 SetReplication 可增加读副本；同一 chunk 的写仍需 primary 排序，更多副本还增加写扇出，不能承诺线性扩展写吞吐。

复制和 scrub 使用独立额度及 governor 限速，初始为每节点后台数据合计 32 MiB/s；复制输入、输出和 scrub 不各自获得完整的独立带宽预算。限制等待在持有大数据缓冲区之前完成。前台不排在后台独占的大队列之后，数据连接拥塞也不能阻断控制心跳。

该速率仅为本机实验起点，真实多机按磁盘、链路和前台 p99 测量调整，不从 2003 年磁盘／网络比例推导当前性能。

## 6. 文件快照和 COW

### 6.1 快照契约与并发范围

Snapshot(source, destination) 创建可写分支。目标必须不存在，父路径有效，目标不能处于源目录树内部；不支持硬链接／符号链接。目录快照为目标生成新 FileId，但共享 ChunkId。

快照给出一个元数据提交点上的文件集合和映射，不提供应用多次写之间的事务，也不修复既有失败区间。源和目标的读取仍受 GFS 一致性模型约束，应用 checkpoint 继续负责定义有效数据边界。

BeginSnapshot 一次性检查源／目标路径和涉及的 chunk 是否存在冲突 COW、修复、迁移或授租准备；冲突则 Busy，不保留部分占用。成功后阻止源子树 create、delete、rename、新租约和新维护操作，读取继续。无关命名空间不受影响；共享同一 chunk 的维护也可能冲突，这是首版的保守串行策略。

### 6.2 快照提交

1. 提交 BeginSnapshot，保存路径范围、源版本、涉及的 chunk 和 pin。
2. 撤销源 chunk 租约，完成所需健康副本的冻结与排空。无法确认的副本排除；没有可信来源时不能完成快照。
3. 提交 CommitSnapshot：确定性遍历源映射，为目标分配新 FileId，复制元数据；每一条目标映射增加对应 chunk 的引用。
4. 在同一事务内发布整个目标树、保存操作结果并释放占用与 pin。共享 chunk 仍不能授予直接写权限。

线性化点是 CommitSnapshot。此前目标不可见，此后目标完整可见。首版元数据复制为 O(文件数 + 映射数)，一次原子提交不复制文件内容，不承诺百万文件目录也能瞬时完成。

Raft 应用中断时从持久事务、last_applied 和操作阶段恢复；不能暴露半棵目标树。客户端断开不自动终止快照，显式终止也必须经状态机确认操作尚未提交。

### 6.3 COW 与映射切换

当 A、B 都映射到 C 时，任一分支写入前：

1. Master 发现 C 的映射引用数大于一，拒绝直接授租。
2. 提交 BeginCow，绑定文件／映射版本与 chunk 索引，分配 C'，登记源 pin、目标资源和操作占用。
3. 在 C 的副本节点本地创建独立 ReplicaId 的 C'，复制长度、字节与校验信息，C 保持冻结。
4. 三个 C' 副本校验、刷盘并持久化 Ready。
5. CommitCow 校验源映射仍指向预期 C，原子切到 C'、减少 C 引用、增加 C' 引用、释放 pin 并保存结果。
6. 对 C' 授予新租约，执行原写请求。

同一映射上的请求加入当前 COW；同一源 chunk 的 COW 首版串行。即使 C 的映射引用数降为一，只要仍有复制读取 pin 或冻结操作，也不能授租；否则尚未完成的复制会读到后来写入。

新 chunk 在文件映射尚未发布时仍由意图 pin 保留，GC 不能因为 refcount 为零收掉它。映射切换、引用与 pin 的变化必须在同一事务完成。

### 6.4 reflink 和持久化

优先使用 rustix 的 FICLONE，在支持且同一文件系统时让两个不同文件共享物理 extent。遇到明确的不支持或跨文件系统条件时执行普通复制，其他 I/O 错误终止并保留上下文，不能统一当作“不支持”。

使用独立临时目标，校验后同步目标及父目录，再发布副本。校验必须使用来源已有的 checksum；不能根据复制出的字节重新生成 checksum 来替代验证。[FICLONE 语义](https://man7.org/linux/man-pages/man2/ioctl_ficlone.2.html)

reflink 减少物理写入，数据校验仍可能扫描整段，不能称整体 COW 为 O(1)。后续共享块分离会消耗空间并可能 ENOSPC；同一节点不同分支共享 extent，不是独立故障副本。

### 6.5 中断与恢复

| 中断点 | 恢复规则 |
| --- | --- |
| 已冻结，尚未提交快照 | 恢复意图继续或提交终止，目标不可见 |
| 仅部分 C' 已复制 | 文件仍指向 C；可恢复复制或终止，新资源后续回收 |
| 映射切换提交，回复丢失 | 查询操作与映射版本，不按超时重复切换 |
| 旧复制在终止后完成 | 禁止发布，临时副本成为孤儿；本地读引用释放前不能修改其来源 |
| 未确认冻结的副本返回 | 重新核验或重建，不直接恢复共享 chunk 的服务资格 |
| 新领导接管未完成操作 | 从持久阶段、占用及本地 Ready 状态继续，不重新猜测源集合 |

GFS 文件快照、文件系统 reflink、Raft snapshot 分别管理文件分支、物理块共享与元数据恢复，必须分开测试和命名。

## 7. 删除、GC 与空间回收

### 7.1 存活根和引用

`mapping_refs(c)` 是所有正常文件及隐藏删除文件中指向 c 的映射边数量；同一 chunk 多次出现须多次计数。`operation_pins(c)` 保留 COW、创建、快照、修复和迁移所需资源。

只有映射引用数和操作 pin 均为零，且没有活动或待恢复的租约／维护操作，chunk 才能退休。引用计数与映射修改原子提交，恢复时提供一致性核对；异常不能当成零继续删除。

### 7.2 文件、chunk 和副本三层回收

文件删除先登记操作并停止新写权限，撤销／排空后提交隐藏删除状态。正常路径消失，但 FileId、原路径信息和映射保留，默认至少 72 小时可恢复。原路径被占用时由调用者指定新路径，恢复后需新租约。显式 Purge 可跳过保留期，不能跳过引用、pin 和排空检查。

保留期结束或 purge 后，提交移除隐藏映射及引用递减。没有存活根的 chunk 进入终态 Retired，之后不能以同一 ChunkId 恢复。chunk 退休和多余副本退休不同：后者还要验证其余布局满足复制目标与故障域要求。

物理删除绑定 ChunkId、ReplicaId 和已提交决策身份，在本地串行边界执行：禁止新操作，等待本地读／复制引用释放，持久化删除意图，unlink 并同步目录，最后清理元数据。重启重放删除意图；目标已经不存在可确认完成，但不能删除同一 ChunkId 的替换实例。

正式副本不会在 Master 不可用时自行按年龄删除。缓存着旧位置的客户端可能读失败并需刷新，不提供 POSIX 打开文件可无限保留远端数据的语义。

### 7.3 保守保留时间

墙上时间只显示删除日期，不决定“至少 72 小时”的安全边界。Raft 状态中维护累计保守运行时间和领导代次／tick 序号。

领导者按 CLOCK_BOOTTIME 测得的实际推进量提交 tick，按最大时钟速率扣除裕量；例如本地间隔 d 至少对应实际 `d/(1+ρ)`。同一代次序号重复不累计，旧代次 tick 不得在新屏障后继续增加时间。tick 回复丢失重试复用身份。

新领导从屏障后的新起点计时，停机和切换期间无法确认的时间不补记。隐藏删除记录以累计时间设回收门槛，因此故障可延长保留期，墙上时间前跳不会缩短。累计时间和 tick 身份进入 Raft snapshot，算术溢出拒绝推进，不能回绕成已过期。

### 7.4 孤儿、未知副本与元数据清理

- 创建先分配并提交意图，未映射的目标仍有 pin；部分完成或操作终止可产生孤儿。
- GC 只有确认意图已终止、无存活引用后才收孤儿；RPC 超时不是终止证明。
- inventory 上报未知 ChunkId 时，等待 Master 完整恢复后提交检查，排除映射和所有创建／恢复意图。
- 小于持久分配器高水位的未知旧 ID，可在上述检查后决定回收；超出已分配范围的异常 ID 隔离调查，不能自动纳入或直接删除。
- Retired 记录在相应副本删除与操作结果不再需要后可清理；节点之后重新带回旧孤儿时，按已分配范围和当前存活根重新作出提交决定，不依赖永久保存每个旧 RPC 墓碑。
- 已提交退休后到达的旧创建／复制完成不能重新发布。即便留下物理文件，也只作为孤儿清理，不能成为文件映射。

扫描、校验和删除均分批并限制后台资源。逻辑释放字节、unlink 字节和 statfs 观测的实际释放量分开记录；reflink extent 仍被其他文件引用时，删除可能不释放相应物理空间。

## 8. 接口、错误和观察

客户端计划提供 mkdir、create、read、write、record_append、stat、rename、delete，以及：

| 接口 | 行为 |
| --- | --- |
| Snapshot(source, destination) | 启动可写分支快照并返回 OperationId |
| GetOperation(operation_id) | 查询进行中、提交或终止结果；记录不存在不证明旧请求从未执行 |
| Undelete(file_id, destination) | 在保留期内原子恢复到无冲突路径 |
| Purge(file_id) | 跳过保留期，仍遵守引用和退休协议 |
| SetReplication(file_id, goal) | 修改复制目标；调整副本走受控复制／退休，新租约按目标就绪 |

元数据变化由具体的 Raft 命令表示：PrepareLease／RenewLease／BeginSnapshot／CommitSnapshot／BeginCow／CommitCow／复制提交／退休等。节点 RPC 分别处理准备／撤销、冻结确认、推送、mutation、本地 clone、复制、发布和退休。请求携带对应 OperationId、预期版本与实例身份。

确定错误包括路径冲突、Busy、陈旧身份、校验失败、磁盘错误和空间不足；传输超时另带是否可能执行的信息。调用者不能将结果不确定重写成确定失败。操作结果记录保留期间可查询，清理记录后不能据缺失自动重放非幂等操作；首版不承诺永久去重和无限期结果找回。

日志记录请求／操作／租约／chunk／副本身份、状态转换、持久化点与错误，不记录整个用户 payload。指标区分读写延迟、RPC 不确定结果、恢复等待、dirty／损坏副本、欠复制、操作 pin、迁移字节和 GC 物理收益。

## 9. 验证、性能实验与实施路线

### 9.1 验证层次

1. 确定性状态机：性质测试检查版本单调、映射与引用一致、共享禁止写、pin 保活、退休不能复活；只对实际模型范围作结论。
2. 本地存储：进程重启与固定故障点验证 redb、数据文件、目录同步和恢复顺序；进程崩溃测试不替代硬件断电实验。
3. 协议与多进程：可控时间、网络代理、固定暂停点、真实 RPC 和节点重启，检查指定事件交错。
4. 性能：固定数据集、并发与冷热缓存条件，记录环境和结果；没有执行前不把目标写成测量事实。

### 9.2 能区分正确与错误的测试矩阵

| 场景 | 必须观察的结果 |
| --- | --- |
| 授租／续租回复迟于期限、nonce 或 BootId 不匹配 | 不激活或延长权限，不从接收时重新计时 |
| now 等于 deadline | 拒绝新的 mutation |
| primary 通过检查后暂停，随后维护或切换 | 新代次不被旧操作覆盖；排空涵盖已准入 I/O |
| secondary 收到迟到 mutation 或 Activate | 持久撤销拒绝旧租约复活 |
| Master 在准备、版本安装、发布、续租各点切换 | 版本不回退，恢复尊重持久阶段与授权等待 |
| 投票／日志写、状态应用、snapshot 安装和清理中断 | 不提前完成持久化回调，不暴露部分状态或删除必需日志 |
| 一个 secondary 部分执行或丢回复 | 返回不确定／失败并停止本代次，不静默缩小集合 |
| 并发普通写跨 chunk | 检查允许的交错，不误判为完整事务 |
| 并发追加、padding、成功回复丢失 | 成功记录至少一次完整出现；允许重复与失败残片 |
| dirty 提交、数据同步、清除 dirty 各点崩溃 | 未验证副本不发布，全部来源不可信时返回不可用 |
| 部分覆盖遇到旧边界损坏 | 不通过新校验和掩盖保留字节损坏 |
| snapshot 与写、create、rename、delete、COW 竞争 | 目标树一次可见，提交后分支修改隔离 |
| 同一共享 chunk 的两个分支分别修改 | 映射版本、引用与各分支数据正确，源 pin 阻止修改 |
| COW 部分完成、提交丢回复、终止后迟到 Ready | 旧映射可恢复，新映射不重复切换，孤儿不发布 |
| reflink 支持／不支持、复制损坏、后续写 ENOSPC | 两种路径语义一致；损坏或错误不能伪装成成功 |
| 复制中来源／目标失败，Ready 后目标再次失效 | 不提前退休来源，不将 staging 计入健康数 |
| GC 与复制、快照、恢复删除竞争 | 活映射和 pin 阻止退休，引用变化原子 |
| 旧删除命令到达替换副本 | 新 ReplicaId 保留 |
| 墙上时间前跳、重复 tick、切换和停机 | 至少保留窗口不缩短；恢复后可继续回收 |
| 恢复时 inventory 报告未知／未来 ID | 不按空索引删除；存活意图保护资源，异常隔离 |
| 容量与 primary 均衡、后台流量饱和 | 滞回和冷却限制反复搬迁；新布局就绪才移除旧实例；控制流仍可运行 |

OpenRaft 存储适配运行官方契约测试并补充以上持久化边界。测试通过不证明任意网络调度和硬件故障下的系统正确性。

### 9.3 负载与测量

端到端场景计划为三个 Master、四个 chunkserver，三副本加修复余量。本机节点有独立目录；跨主机故障结论需要真实多机验证。

实验固定并记录数据集、文件数、文件大小、请求大小、读写／追加比例、客户端数、热度分布和缓存条件。比较 64／128／256 MiB chunk、数据窗口、普通复制与 reflink、以及保持持久化顺序的批量策略。

报告吞吐、p50／p95／p99、CPU、RSS、刷盘次数、磁盘读写量、snapshot 元数据暂停时间、COW 延迟、修复对前台 p99 的影响、均衡收敛与搬迁量、GC 扫描与实际空间收益。记录 CPU、存储介质、文件系统、内核、网络、构建与依赖版本。

初版不引入 RDMA、QUIC、纠删码、自制 io_uring 层或在线增量追赶。只有测量表明现有协议的具体瓶颈时，再为优化单独记录语义、代价和反例验证。
