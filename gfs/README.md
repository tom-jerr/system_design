# GFS in Rust：论文机制复现与现代化设计

本模块以 [The Google File System（SOSP 2003）](https://pdos.csail.mit.edu/6.824/papers/gfs.pdf)为基础，学习大文件存储中的复制顺序、租约、故障恢复、快照和空间回收。目录与 `shard_kv/` 同级，后续采用独立的 Rust Cargo 项目。

**当前只有设计文档和实施路线，没有 Cargo 项目、可运行服务或 GFS 测试结果。** 下文的接口、默认值和保证都是待实现、待验证的目标。不要将此目录视为已经可部署的文件系统。

## 目标与运行场景

面向学习和故障实验：先在 Linux 本机运行独立进程、独立数据目录，再扩展到多机。使用 TCP，不要求各节点共享目录；客户端只通过 RPC 访问远端数据。

目标负载为大文件顺序读取、顺序写入及多客户端 record append，同时支持论文中的普通覆盖写。保留 primary 排序、流水线传输、失败写入可能部分生效、至少一次追加等语义，不把文件内容提升为线性一致事务。

元数据采用 OpenRaft 自动选主，chunk 复制仍采用 GFS primary/secondary 协议。项目自行实现的学习机制是 GFS 的租约、复制、恢复、COW 和 GC；网络框架、序列化、事务存储、校验算法等复用成熟库。

## 计划组件

| 能力 | 计划选择 | 应用仍负责的边界 |
| --- | --- | --- |
| 运行时与 RPC | Tokio、tonic、prost、tonic-prost-build | 有界资源、错误分类、结果不确定性与重试 |
| 元数据共识 | OpenRaft | 网络适配、持久化适配、读屏障、切换后的 chunk 权限恢复 |
| 持久元数据 | redb，立即持久化事务 | 与数据文件之间的写入顺序和崩溃恢复 |
| chunk 数据 | 普通 Linux 文件与页缓存 | 刷盘、目录同步、校验、dirty 隔离 |
| 校验与系统调用 | crc32c、rustix | 校验覆盖范围、reflink 的适用条件和失败行为 |
| 后台限速 | governor、Tokio semaphore | 修复、scrub 与前台流量的资源隔离 |
| 工程设施 | tracing、clap、thiserror、tempfile | 有上下文的诊断、CLI 和隔离实验 |

初始版本基线为 tonic 系列 `0.14`、prost `0.14`、OpenRaft `0.9.25`、redb `4.4`。这些是设计参考版本，尚未安装到本模块，也没有本模块的锁文件；进入实现阶段时须核对兼容性、MSRV 和具体 API，提交 `Cargo.lock`。

## 初始参数与重要限制

| 项目 | 设计初值 |
| --- | --- |
| chunk / 校验块 | 64 MiB / 64 KiB |
| 默认复制目标 | 三副本；新写租约需三个健康副本就绪 |
| primary 租约 | 60 秒；有写入活动时每 20 秒尝试续租 |
| 心跳 / 数据帧 | 1 秒 / 256 KiB |
| record append 上限 | 16 MiB，空间不足先 padding 再转下一 chunk |
| 隐藏删除保留期 | 至少 72 小时保守累计运行时间；故障可延后回收 |
| 均衡评估周期 | 60 秒 |
| 后台复制并发 | 每节点一个输入、一个输出，全局最多四个 |
| 后台数据速率 | 每节点合计 32 MiB/s，属于本机实验初值 |

主要边界：

- Master 元数据通过 Raft 多数派提交；chunk 写成功需要该租约所有参与副本持久化，二者不是同一个复制协议。
- 副本不足时允许从健康副本读取，先修复到复制目标再恢复新写租约。记录复制目标可调整，不同目标的实际故障容忍度不同。
- 租约依赖持续推进且速率误差有界的时钟；过期不撤销已经接受的操作，维护协议还需撤销和排空。
- 超时、断连和取消不能证明远端未执行；追加允许重复，跨 chunk 写入不原子。
- dirty 副本重启后隔离并从健康来源恢复。所有来源同时丢失或需要隔离时可不可用，不承诺任意多节点故障下恢复。
- 文件快照为可写分支，不修复既有失败写入，也不代替应用 checkpoint。它与 Raft snapshot、文件系统 reflink 是三个机制。
- 本机的逻辑主机／机架标签只用于协议实验，不能证明独立磁盘、电源和网络故障的隔离能力。

## 分阶段实施与验收

所有阶段当前均为**待实现**。每阶段只新增为当前行为所需的状态和接口，并将实际验证结果写入设计记录。

| 阶段 | 实施内容 | 退出条件 |
| --- | --- | --- |
| M1：状态与持久化 | 身份与分配器、确定性状态机、长操作意图、OpenRaft 网络与 redb 适配、Raft snapshot | 存储契约测试通过；日志、投票、状态机、snapshot 在指定崩溃边界能恢复 |
| M2：租约与读写 | 授租／续租／撤销／排空、普通复制读写、校验和、dirty 恢复、流式推送 | 正常写在全部参与副本持久化；迟到旧操作不能覆盖新代次；损坏数据不会被正常返回 |
| M3：追加与恢复 | record append、padding、Master 切换、inventory 重建、修复和布局变更 | 成功记录完整出现至少一次；切换不复活旧权限；单副本故障后可读、可修复并恢复写入 |
| M4：快照与 COW | 路径范围占用、原子快照提交、COW 映射切换、reflink 与普通复制 | 两个分支修改隔离；每个中断阶段能继续或终止；源与目标引用数一致 |
| M5：删除与 GC | 隐藏删除、恢复、purge、操作 pin、保守时间、孤儿和副本退休 | 活引用和 pin 阻止删除；旧删除不影响替换实例；恢复窗口不因时钟前跳而缩短 |
| M6：均衡与测量 | 放置、容量／primary 均衡、读分散、后台限流、性能实验 | 新副本就绪后才退休旧副本；均衡能收敛并报告搬迁代价；优化有匹配负载的测量依据 |

M1 创建 Cargo 项目时，再将实际存在的 manifest 加入仓库编辑器项目列表。后续入口计划包含 Master、chunkserver 和客户端 CLI；当前不提供占位二进制或无法执行的启动命令。

端到端实验计划使用三个 Master、四个 chunkserver，其中一个提供三副本故障后的修复余量。测试采用固定故障点、可控时间和网络代理，结合真实进程重启；结果仅适用于实际注入的故障和时序。
