# 单机 KV 与租约锁设计

## 目标与依据

本模块是单个服务端、多个客户端的学习原型：键和值为字符串，状态仅保存在服务进程内。客户端通过 TCP RPC 访问服务端；服务端持续运行时，客户端进程崩溃、消息丢失或回复延迟属于本设计关注的故障。服务器崩溃恢复、持久化、复制和机器间信任不属于当前保证。

[6.5840 Lab 2](https://pdos.csail.mit.edu/6.824/labs/lab-kvsrv1.html) 要求按版本条件写、线性一致、重发时至多一次生效，以及无法判断写入是否发生时返回 `ErrMaybe`。课程原实验通过 KV 的 `Get/Put` 组合实现锁，并假设持锁客户端不崩溃。本项目按用户需求扩展为服务端租约锁 RPC 和 fencing 校验；两者是本项目的设计选择，不是课程原规格。这里的 Rust RPC 和测试也不直接兼容课程的 Go 测试程序。

## 选择与权衡

- Tokio 提供异步运行时和网络 IO；`tarpc` 的 TCP Serde transport 提供 RPC 和请求截止时间。超时、断连或取消不证明服务端没有执行请求，重试语义由 Clerk 和本服务负责。[tarpc 文档](https://docs.rs/tarpc/latest/tarpc/)
- 一个 `std::sync::Mutex` 保护 KV 和锁状态，临界区只做同步内存操作。`Get` 的读取、条件写的检查与更新，以及 fencing 检查与写入都在锁内完成。一个简单的全局锁足以表达操作顺序；Tokio 的异步 Mutex 允许跨 `.await` 持锁，而这里不需要这一能力。[Tokio Mutex 文档](https://docs.rs/tokio/latest/tokio/sync/struct.Mutex.html)
- `tonic` 提供 gRPC/HTTP/2 与跨语言接口；本实验只有 Rust 客户端和服务端，选用 tarpc 减少 Protobuf 定义与生成步骤。普通内存 `HashMap` 足以表达版本状态，暂不引入持久化 KV 引擎或并发 map。
- TCP 的长度字段是四字节，客户端和服务端将最大帧长度设为 `u32::MAX`，避免 tarpc 默认 8 MiB 限制使正常大值反复失败。JSON 编码后的单帧不能超过该长度；本学习原型假设可信客户端，未限制并发连接或内存分配，也未做负载测试。

## 状态、不变量与失败边界

每个键记录 `(value, version)`，新键只接受版本 `0` 的写入并变为版本 `1`；已有键仅在版本相等时原子写入并递增版本。不同步操作在同一把互斥锁内观察与改变状态，因此成功和失败的条件判断都有一个状态操作时的线性化点。版本用 `u64`，递增溢出返回明确错误，状态不变。

每个锁名有独立的 fencing 计数、当前持有者及单调时钟期限。服务端在进入状态临界区后读取当前时间；`now < deadline` 才有效，等于截止时间即失效。新获取递增 token，续租和释放仅接受当前 acquisition ID、token 和有效期限。锁状态在请求时检查过期；无需后台清理任务，过期后的下一次获取即可接管。计数溢出时拒绝新获取。

客户端为每次获取生成 UUIDv4 acquisition ID；同一请求因回复丢失重试时复用 ID。身份不冲突依赖随机 UUID 不发生碰撞。在当前租约存活时，重复获取返回同一 token，不能延长期限。已经授予过的 ID 会被保留，即使租约过期或释放也不能再次授予，因此**曾成功授予的同一获取请求**迟到重发时不会重新占用锁。这需要为每次成功获取保留一条内存记录，空间随获取次数增长，是当前协议的资源边界。

如果一个 ID 曾收到 `Busy`、从未被授予，而客户端放弃后它的旧请求才在锁空闲时到达，服务端无法从这个 ID 判断客户端已离开，可能给它授予一个无人使用的租约。该租约没有续租时会过期；有有限个在途请求、服务端时钟推进且后续请求能送达时，等待者最终可以获得锁。`delayed_never_granted_attempt_can_temporarily_acquire_after_client_leaves` 用确定时间构造了这个反例；墓碑只针对曾授予的 ID，并不消除这类暂时的活性影响。

持有者周期性续租；崩溃停止续租后，租约在最后一次被服务端接受的续租之后到期。崩溃时已在途的续租仍可能在原期限前到达并延长租约；超时只是失联，不能证明对方已经停止。新客户端能否完成获取还依赖服务器运行、时钟推进、网络和调度最终恢复。[租约与 fencing 的故障分析](https://martin.kleppmann.com/2016/02/08/how-to-do-distributed-locking.html)

服务端在同一临界区校验当前 token、租约期限和 KV 版本后执行 `PutFenced`。所以旧进程恢复或旧请求迟到后，不能以旧 token 改写本 KV 服务，也不能释放或续租新持有者的锁。普通 `Put` 是不受锁保护的操作；应用必须为同一受保护资源约定相同锁名并使用 `PutFenced`。其他存储、外部 API 或本地副作用只有在各自的资源端校验 token 时才受到 fencing 保护；客户端检查本地租约状态或取消续租都不是最终正确性边界。

服务端和锁 token 都只在内存中。服务端重启会丢失 KV、租约、token 与已授予 ID，不能以本实现跨服务端重启为外部资源提供持续递增的 fencing token。后续 Raft 要单独设计复制、持久化、快照、领导者切换以及线性一致读；当前状态机不提供这些保证。

## 获取身份与 fencing 的关系

锁名标识锁；客户端生成的 acquisition ID 标识一次获取及其重试，服务端在授予时生成的 fencing token 标识一个锁代次。当前接口将 acquisition ID 用于重复获取、续租和释放，但锁机制并不要求 ID 必须是 UUID。随机 ID 与永久墓碑的组合导致状态随历史成功授予次数增长；问题来自当前去重契约和协议，不是所有使用 UUID 的锁都必须永久保存历史。

只删除墓碑、保留 token 计数器不能维持现有的重复获取语义：旧 `TryAcquire(lock, id)` 请求在空闲时不携带旧 token，服务端会把它当新请求并分配**更高的新 token**，资源的最大 token 检查也无法识别其请求身份。单元测试 `counterexample_removing_tombstones_without_generation_check` 在测试中移除墓碑，复现了这一反例；它不是当前生产状态转换。

一种可研究的替代方案是在获取请求中携带客户端观察到的锁 generation，服务端仅在 generation 匹配时授予并递增。只保留当前租约的 acquisition ID，就可以识别活跃的同一次重试；曾获授请求的旧 generation 在租约结束后不再通过检查，锁状态可降为每个锁名一个计数器和当前租约。该方案需要新增读取 generation 的接口并重新定义冲突和回复丢失后的恢复。

也可以完全去掉 acquisition ID，只使用 generation 条件获取和授予后的 token。但两个客户端可能观察到相同 generation：其中一个获取成功、回复丢失后，客户端不能仅凭 generation 变化判断赢家是谁。它必须把结果当成不确定，不能猜测自己持有新 token；可以等待可能存在的租约过期，再重新尝试。这保留安全性，但牺牲了当前接口在租约存活期间通过同一 ID 找回原 token 的能力。续租和释放在可信客户端及 token 在服务端生命周期内不重用的假设下，可以只检查锁名和 token。

以上两种替代都不能识别所有尚未获授的已放弃请求：若该请求观察到的 generation 仍是当前值，它仍可能获得一个暂时租约；要拒绝这种请求还需要明确的会话失效或请求有效期语义。客户端会话、并发请求、服务重启以及代次持久化需单独设计；这里没有实现这些替代方案。

Chubby 的 sequencer 含锁名、模式与 lock generation，资源可依据锁服务状态或已观察到的 sequencer 检查访问；论文并未说明仅凭 fencing token 就能识别首次到达的旧获取。[Chubby 论文 §2.4](https://research.google.com/archive/chubby-osdi06.pdf) 若外部资源只维护已见最大 token，旧 token 在资源收到较新 token **之后**会被拒绝；资源尚未观察到新 token 时，仅比较最大值无法立即知晓服务端刚发生的转移。本原型的 `PutFenced` 因锁与 KV 同在一个临界区，直接校验当前代次及期限，保证范围更具体。单调计数器也必须按锁名保留；即使锁当前空闲，随意删除计数器并重建会重用旧 token。

## 请求重试

Clerk 在 RPC 没收到回复时重试，Put 保持原始版本。一个版本只能成功写一次；若第一次回复就返回版本不匹配，这是确定的 `Version`。若此前有尝试没有回复，重试返回版本不匹配时用 `Maybe` 表示写入可能已经发生；不能把它当成失败。`PutFenced` 重试时若租约已经失效，同样可能是第一次写成功后回复丢失，必须保守返回 `Maybe`。

取消或网络错误不等于撤销已执行的状态转换。不可恢复的编解码错误会返回 `Transport`，写入结果可能已经发生时通过 `MaybeWithCause` 保留其原因；不会对同一确定错误无限重试。租约续租无法确认时，客户端不再依赖本地锁状态，但最终由服务端 `PutFenced` 以及资源侧 fencing 判断写入是否有效。

## 验证边界

测试参考本机官方 `6.5840-golabs-2024`（commit `db55e49c10e1021c3587bb2364bee36013ad9c66`）中 `src/labrpc/labrpc.go` 的丢请求、丢回复、断连和延迟/重排，以及 `src/kvsrv/test_test.go` 记录并检查并发操作历史的思路；课程 2026 版版本化 `Put` 语义以链接中的实验说明为准。测试用本项目的 Rust RPC 和条件写模型重新构造，不直接运行或声称通过 Go 测试。

本次 `cargo test` 通过 6 个状态机单元测试和 26 个集成测试（包含子进程入口），`cargo clippy --all-targets -- -D warnings` 通过。测试覆盖条件写与并发读、期限边界、重复请求、多次丢请求/回复、延迟与乱序、部分帧、请求取消、客户端分区和崩溃、租约续租和释放、旧 token 迟到操作、多个客户端竞争、超出默认 8 MiB 帧上限的数据，以及小规模历史的穷举检查；带丢回复的并发历史运行五轮。另对并发历史、客户端分区、延迟请求、释放与写竞争、锁竞争五个测试各重复三次，全部通过。50,000 次单键 Put 的状态机测试检查逻辑状态没有按请求增加记录，但不是堆内存或 RSS 测量，也不覆盖租约墓碑的增长。

历史检查器只处理测试中已完成的单键 `Get/Put`、版本冲突和 `Maybe`，按键分别穷举短历史；它不是课程的 Porcupine 实现，也没有对所有可能的请求交错做模型检查。测试只覆盖其注入的事件和时序；不能证明任意网络调度、服务端重启恢复或未来 Raft 实现的正确性。
